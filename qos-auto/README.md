# 두 맥북으로 UDP 손실과 부하별 응답 지연 측정하기

iperf3의 C 라이브러리(libiperf)로 UDP 데이터를 보내고, 별도 UDP 응답기로 작은 요청의 왕복 시간(RTT)을 측정합니다. 송신 방향은 보검님의 맥북 → 상대방 맥북입니다. 이 폴더의 모든 측정·분석 코드는 C로 작성했습니다. Makefile은 빌드 명령을 담습니다.

## 1. 두 맥북에서 준비

1. 두 맥북을 같은 Wi-Fi에 연결합니다. 예시는 상대방 IPv4가 `192.168.0.25`, 보검님 IPv4가 `192.168.0.28`인 경우입니다. 현재 주소가 다르면 명령 안의 IP를 바꿉니다.
2. 두 사람 모두 GitHub 저장소에서 `leejuhyoung` 브랜치를 받습니다. `qos-auto` 폴더는 `src`와 같은 위치에 있으며 iperf3 소스와 함께 빌드합니다.
3. 각자 VS Code에서 `configure`, `src`, `qos-auto`가 보이는 폴더를 열고 **터미널 → 새 터미널**을 누릅니다. 터미널에서 위치와 파일을 확인합니다.

```sh
pwd
ls qos-auto/Makefile src/iperf_api.h
```

상대방도 자기 맥북의 실제 프로젝트 위치에서 진행합니다. 경로를 모르면 터미널에 `cd `를 입력하고 Finder에서 프로젝트 폴더를 끌어다 놓은 뒤 Enter를 누릅니다.

## 2. 빌드

기존 실습에서 이미 libiperf를 빌드했다면 다음 한 줄부터 실행합니다.

```sh
make -C qos-auto CC=clang && ./qos-auto/qos --help
```

처음 빌드하거나 `src/.libs/libiperf.a`가 없으면, iperf3 소스 최상위 폴더에서 실행합니다. OpenSSL 인증 기능을 사용하지 않는 실습용 정적 빌드입니다.

```sh
./configure --disable-shared --enable-static --without-openssl
make -j4
make -C qos-auto CC=clang
./qos-auto/qos --help
```

도움말에 `scan SERVER_IPV4 --loss PCT --rtt-p95 MS`가 나오면 새 버전입니다. 검증에 사용한 iperf3 소스 커밋은 `3794b9fd8c1b3dffa45f60981a371645bb6ad0fb`입니다. 이 소스의 `iperf_api.h`, `cjson.h`, configure가 만드는 `iperf_config.h`가 필요합니다.

## 3. 상대방 맥북에서 터미널 두 개 열기

터미널 ①에서 iperf3 서버를 실행합니다. 이미 오늘의 서버 주소에서 5201 포트를 열고 대기 중이라면 계속 사용합니다.

```sh
./src/iperf3 -s -B 192.168.0.25
```

`Server listening on 5201`이 보이면 이 창을 열어 둡니다. 터미널 ②에서 RTT 응답기를 켭니다. 명령의 첫 번째 IP는 상대방 맥북, 두 번째는 보검님 맥북입니다.

```sh
./qos-auto/qos echo 192.168.0.25 192.168.0.28
```

`UDP echo 192.168.0.25:5202, client 192.168.0.28`이 표시됩니다. 5201은 iperf3의 TCP 제어·UDP 데이터 포트이고 5202는 추가한 UDP 응답기 포트입니다. 두 창 모두 실험이 끝나면 Control+C로 닫습니다.

## 4. 보검님 맥북에서 자동 탐색 → 전후 측정

아래 명령은 모두 프로젝트 최상위 폴더에서 실행합니다.

```sh
mkdir -p results
./qos-auto/qos scan 192.168.0.25 --loss 1 --rtt-p95 40 --out results/plan-auto.json
```

`--loss 1`은 허용 수신 손실률 1%입니다. `--rtt-p95 40`은 다음 단계에서 허용할 RTT p95 40 ms입니다. 기본 자동 탐색은 속도 상한 입력 없이 실행합니다. 실습 범위를 제한하고 싶은 경우에만 `--cap 30`처럼 Mbps 단위 상한을 추가합니다. `--out`을 생략하면 `results/plan.json`에 저장합니다. 기존 파일을 보호하므로 새 실험은 새 파일명을 사용하세요.

`Selected target`과 `Saved plan`이 나온 다음, **공유기 설정을 바꾸기 전에** 실행합니다.

```sh
./qos-auto/qos profile results/plan-auto.json results/before-auto.json
```

before 파일이 만들어지면 비교하고 싶은 공유기 설정 한 가지를 바꿉니다. Wi-Fi에 다시 연결된 경우 서버·클라이언트 IP가 같은지 확인합니다. 같은 장비·위치·서버·방향을 유지하고 **위에서 저장한 계획 파일을 그대로** 사용합니다.

```sh
./qos-auto/qos profile results/plan-auto.json results/after-auto.json
./qos-auto/qos compare results/before-auto.json results/after-auto.json
```

공유기 설정을 바꾸지 않고 두 번 실행하면 평상시 반복 측정 차이를 관찰할 수도 있습니다. 한 대에서 실행 흐름만 확인하려면 서버·응답기·클라이언트 주소를 모두 `127.0.0.1`로 바꾸고, 첫 탐색에 `--cap 2`를 넣으면 짧게 확인할 수 있습니다.

## 5. 기능별 판정 규칙

### ① 손실률 기반 속도 탐색

- 최초 목표는 1 Mbps이고, 통과하면 2, 4, 8 Mbps처럼 두 배로 올립니다. 매 후보에서 1,200바이트 UDP 데이터그램, 단일 스트림, 5초씩 3회 측정합니다.
- 세 번 모두 실제 송신률이 목표의 ±5% 안이고 수신 손실률이 허용치 이하면 합격합니다. 손실률은 수신 측 `end.sum_received.lost_percent`에서 읽습니다. 송신률이 벗어나면 경계를 단정할 수 없어 탐색을 멈추고 이전 합격 후보가 있으면 그중에서 선택합니다.
- 처음부터 실패하면 절반으로 내려가며 합격 지점을 찾습니다. 탐색 최저 속도는 0.1 Mbps입니다. 합격·실패 양쪽이 생기면 중간값을 시험하며 구간을 좁힙니다. 종료 폭은 합격 쪽 속도의 1/8이고 최소 0.025 Mbps, 최대 1 Mbps입니다.
- 후보는 최대 24개까지 시험합니다. 구현에서 다루는 최고 속도는 10,000 Mbps입니다. 끝까지 합격하면 마지막 측정 범위까지 통과했다고 표시합니다. 후보당 데이터 송신은 총 15초이며 실제 실행에는 연결·대기 시간이 더해집니다.
- 합격 후보마다 실제 수신 처리량 3개의 중앙값을 구하고 그 값이 가장 큰 후보의 목표 송신률을 선택합니다. 최고 수신 중앙값이 같은 경우 더 낮은 목표를 선택합니다. 합격 후보가 없으면 계획 파일을 만들지 않습니다.
- 예를 들어 16 Mbps 합격, 32 Mbps 실패라면 다음 후보는 24 Mbps입니다. 24 Mbps도 실패하면 20 Mbps를 시험합니다. 시간에 따라 달라지는 Wi-Fi에서는 결과를 이번에 실제로 시험한 후보 범위 안에서 해석합니다.

### ② 부하별 RTT와 응답 누락률

선택된 **목표 송신률**이 20 Mbps라면 단계는 0, 5, 10, 15, 20 Mbps입니다. 0%는 작은 요청만 보내는 무부하 기준입니다. 유부하 단계에서는 iperf 시험 시작 콜백이 별도 스레드를 시작합니다. 750 ms 후부터 75 ms마다 12바이트 UDP 요청을 보내고 보검님 맥북의 단조 시계로 RTT를 잽니다. 응답 기한은 500 ms입니다.

각 단계에서 40개씩 3회, 총 120개를 시도합니다. 기한 내 응답한 표본을 모아 정렬하고 `ceil(응답 개수 × 0.95)`번째 RTT를 출력합니다. 120개 모두 응답했다면 114번째 값입니다. 늦었거나 누락된 응답은 별도로 집계합니다. 일부 응답이 빠지면 성공한 요청의 p95만 낮게 보일 수 있으므로 `probe missing`을 함께 확인하세요. 회차 전체에 응답이 없으면 그 단계는 판정 보류입니다.

### ③ 전후 비교

같은 계획인지 먼저 검사하고, 실제 송신률이 양쪽 모두 목표의 ±5% 안인지, 대응 회차의 전후 실제 송신률 차이도 목표의 5% 이내인지 검사합니다. 비교 가능한 단계에서 수신 손실률 최댓값(3회)과 단계 RTT p95가 모두 허용치 이하면 합격입니다. 무부하는 RTT 기준선으로 사용하며 최고 합격 송신률 계산에서는 제외합니다.

| 출력 | 읽는 법 |
| --- | --- |
| Selected target / median received | 선택한 목표 송신률 / 해당 후보의 수신 처리량 중앙값 |
| RTT p95 / probe missing | 기한 내 응답의 지연 p95 / 누락·시간 초과 비율 |
| RTT p95 change (after - before) | 같은 부하의 전후 지연 차이. 음수면 지연 감소 |
| Highest joint PASS change | 비교 가능 단계 중 손실·지연 기준을 함께 통과한 최고 목표 송신률의 변화. 양수면 상승 |
| INCONCLUSIVE / Excluded | 실제 부하 또는 RTT 자료가 판정 조건을 충족하지 못한 단계 |

예를 들어 변경 전후 10 Mbps에서 p95가 45 → 25 ms라면 차이는 −20 ms입니다. 최고 단계가 전후 모두 통과하면 더 높은 속도에서의 개선은 이 계획으로 측정되지 않습니다.

## 문제 해결

| 증상 | 확인할 것 |
| --- | --- |
| make: qos-auto: No such file or directory | 프로젝트 최상위 폴더인지, `qos-auto`가 포함된 브랜치를 받았는지 확인합니다. |
| No rule to make target ...libiperf.a 또는 iperf_config.h 없음 | 2단계의 configure와 make를 iperf3 최상위 폴더에서 실행합니다. |
| No route to host / connection refused | 상대방 현재 IP, 같은 Wi-Fi, 상대방 터미널 ①의 대기 상태를 확인합니다. |
| scan은 성공하고 profile에서 응답이 없음 | 상대방 터미널 ②가 실행 중인지, echo의 두 번째 IP가 보검님 주소인지 확인합니다. |
| output already exists | 새 측정에는 새 출력 파일명을 쓰고, 전후 profile의 입력은 동일한 plan으로 유지합니다. |
| no passing candidate | 실제 송신률과 수신 손실률, 마지막 종료 이유를 확인합니다. |

## 코드를 읽는 순서

1. `main.c` — 명령과 `--loss`, `--rtt-p95`, `--cap`, `--out` 해석
2. `scan.c` — `scan_auto()`의 두 배 증가·반감·중간값 탐색과 `candidate()`의 3회 판정
3. `load.c` — libiperf UDP 전송, 실제 송수신 속도와 손실률 읽기
4. `probe.c` — 요청 전송, UDP 응답기, 순번 확인, RTT 측정
5. `profile.c` — 단계별 p95, 응답 누락률, 두 결과의 차이 계산
6. `plan.c`, `qos.h` — JSON 계획 저장·검사와 측정 상수

이전 실습의 위치 인자 방식인 `scan 서버IP 손실률 상한 지연기준 계획파일`도 기존 고정 상한 격자로 동작합니다. 새로운 자동 탐색을 하려면 4단계의 이름 있는 옵션을 사용하세요.
